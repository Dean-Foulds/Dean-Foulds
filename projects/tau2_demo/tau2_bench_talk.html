03 / 18 — Act I
The Production Mismatch
  • Benchmarks report accuracy(single trial) — success rate averaged across tasks, one run per task.
  • Production agents run the same class of task hundreds or thousands of times. A refund agent handles 500 requests/day.
  • Under repeated execution, per-trial error rate perr = 1−p compounds: n failures in N runs ≈ N·perr.
  • Crucially: failure at turn k of a multi-turn interaction often invalidates all subsequent turns — error is non-recoverable.
An agent with p=0.90 running 500 tasks/day will fail on ~50 tasks daily. If failures are silent, this is a systemic problem invisible to benchmark numbers.
FAILURE COUNT DISTRIBUTION (N=1000, p=0.82)
σ² = N·p·(1−p) → σ ≈ 13.0 failures
04 / 18 — Act II
τ-bench: Design Rationale
1
Dual-LLM simulation
An agent LLM and a user simulator LLM interact autonomously. Human raters not required at inference time.
2
Tool-augmented agent
Agent has access to structured tools (database lookups, action APIs). Evaluation includes tool use correctness, not just dialogue quality.
3
Policy-grounded scoring
Each domain provides a formal policy document. Success is binary: did the agent resolve the task while following policy?
4
k-trial evaluation
Each task is run k times independently. Passk measures the fraction of tasks passed on all k trials.
Domains (τ-bench v1):

RETAIL — 115 tasks: product lookup, order management, returns, exchanges

AIRLINE — 50 tasks: rebooking, cancellations, seat changes, refunds
τ²-bench adds: telecom domain + adversarial user scripting + multi-agent evaluation. We cover this in Act IV.
05 / 18 — Act III
The Passk Metric
Passk(taski) = pik
pi = Pr[agent passes task i on one trial]
Passk(benchmark) = (1/N) · Σi=1..N pik
  • Pass1 is the standard accuracy metric. It treats each trial as independent and reports the mean.
  • Passk asks: what fraction of tasks does the agent solve reliably — passing every one of k independent attempts?
  • Because pi ≤ 1, Passk is monotone decreasing in k. The rate of decrease reveals the variance structure.
  • A task where pi=1.0 contributes the same to Passk for all k. Only unreliable tasks cause decay.

Key observation: p=0.95 vs p=0.80 differ by 15pp at k=1. At k=8 they differ by 49pp — a 3× amplification of the reliability gap.
06 / 18 — Act III
Reliability Decay as k Increases
Models that appear within noise at k=1 diverge substantially by k=8. Ranking order can invert — validate at the k that matches your deployment cadence.
07 / 18 — Act III
Pass¹ vs Pass⁸: Quantifying the Gap
Pass¹ — single-trial accuracy
82%
  • Standard benchmark metric. One run per task.
  • Hides within-agent variance across trials.
  • Maps poorly to production: agents don't run once.
  • Inflated by lucky samples and partially-correct outputs.
Pass⁸ — 8-trial reliability
20%
  • Same agent, same tasks — 8 independent runs each.
  • Reveals compounding failure probability.
  • Maps directly to per-session or per-day reliability.
  • Identifies agents worth deploying vs. agents needing work.
The 35% relative increase in the benchmark gap (3pp → 62pp) between k=1 and k=8 is not an artefact — it is the mathematical consequence of compounding independent errors.
08 / 18 — Act IV
τ²-bench: Three Extensions
EXTENSION 01
Adversarial User Simulation
  • User LLM is scripted with failure modes: contradiction, scope creep, policy pressure, ambiguity injection.
  • Tests agent robustness, not just capability.
  • Typical pass rate reduction: −15 to −30pp vs cooperative baseline.
EXTENSION 02
Multi-Agent Pipelines
  • Orchestrator + specialised sub-agents evaluated end-to-end.
  • Failure attribution: orchestration layer vs execution layer.
  • Passk compounds across agents: porch·psub < min(porch, psub).
EXTENSION 03
Multi-Turn Complexity
  • Tasks require 6–12 turns with sustained coherence.
  • Error at turn t invalidates turns t+1..T (non-recoverable error model).
  • New domain: telecom, expanding coverage beyond airline/retail.
τ²-bench's central empirical finding: reliability gaps that appear large on τ-bench grow further under adversarial conditions. The ordering across models becomes more pronounced, not less.
09 / 18 — Act IV
Adversarial User Simulation: Failure Modes
  • Contradiction: user changes requirements mid-conversation ("I said aisle — actually, window").
  • Scope creep: user adds unrelated requests once agent is committed ("while you're at it, can you also...").
  • Policy pressure: user pushes for outcomes outside policy, claims ignorance, emotional escalation.
  • Ambiguity injection: underspecified requests that force the agent to clarify or guess incorrectly.
  • Supervisor escalation: user requests escalation regardless of agent response.
Experimental finding (illustrative):
Mean pass rate under cooperative user: 78%
Mean pass rate under adversarial user: 54%
Δ = −24pp — but the variance across models increases, making model selection more meaningful.
Why this matters: if you evaluate only with cooperative simulated users, you are measuring a best-case distribution. Production users are adversarial in the statistical sense — their goals only partially align with what your policy permits.

Variance in the Passk Decomposition
Agent A — Low variance
pi ≈ 0.75 ∀ i
Uniform reliability across all tasks
Pass⁸ = 0.75⁸ ≈ 10%
Agent B — High variance (bimodal)
pi ∈ {0.0, 1.0}
Half tasks: p=1.0 always pass
Half tasks: p=0.0 always fail
Pass⁸ = 50% of tasks · 1.0 = 50%
  • Both agents have mean p ≈ 0.5. Agent B has dramatically higher Passk.
  • Passk rewards task-level specialisation — being perfectly reliable on a subset outperforms uniform mediocrity.
  • This is a feature, not a bug: it maps to the real deployment decision of routing tasks to specialised agents.
  • Implication: profile Passk by task category, not just aggregate. The average can obscure deployable sub-domains.
τ²-bench reports per-task Passk alongside aggregate, which enables this kind of sub-domain analysis.

Statistical Precision Requirements
CI width = 2z · √(p̂(1−p̂)/n)
For ±5pp at 95%: z=1.96, target CI=0.10
→ n ≥ (1.96/0.10)² · p(1−p)
→ n ≥ 384 at p=0.5 (worst case)
k = 1
~50
trials for ±10pp CI
k = 4
~200
trials for ±5pp CI
k = 8
~400
trials for ±5pp CI
  • Each additional trial multiplies evaluation cost linearly. k=8 costs 8× k=1.
  • τ²-bench defaults to k=4 as a compromise between precision and cost.
  • Importance sampling on high-variance tasks reduces cost while preserving statistical validity.
  • Stratified task selection ensures rare failure modes are represented.
Practical heuristic: use k=3 for development (fast feedback), k=8 for pre-deployment decisions. Increase k for tasks with known high variance.
15 / 18 — Act VI
Practical Guidance for Practitioners
# Action Rationale
01 Report Passk, not Pass¹ Calibrate k to your deployment: daily task → k ≥ 7
02 Add adversarial user scenarios Cooperative users in eval ≠ real user distribution
03 Profile Passk by task category Aggregate can hide deployable high-reliability sub-domains
04 Evaluate the pipeline, not just the model Orchestration errors are a distinct failure class
05 Track variance, not just mean pass rate High variance signals brittle tasks worth routing elsewhere
Choosing k in production:
If a task runs f times/day and you want p(zero failures/week) ≥ 0.95, you need Pass7f ≥ 0.95, which requires p ≥ 0.951/(7f). For f=10: p ≥ 0.9993.
The design principle: don't ask "does the agent work?" Ask "what is the probability that the agent works for the next 100 requests?" These are different questions with very different answers.
16 / 18 — Act VII
Open Problems
  • Efficient Passk estimation. How do we estimate Pass8 with 50 trials rather than 400? Current importance sampling approaches reduce cost but do not yet achieve this.
  • Task distribution shift. τ-bench tasks are fixed at benchmark creation time. Real user distributions drift. Adaptation to downstream distributions is an open research problem.
  • Cross-agent contamination. In multi-agent systems, does one agent's failure mode systematically affect another's? Error propagation in directed acyclic agent graphs is under-studied.
  • Goodhart's law. Once Passk becomes an optimisation target, what does the model sacrifice to achieve it? Are there adversarial high-Passk behaviours that are low-utility?
"When a measure becomes a target, it ceases to be a good measure." — Goodhart (1975), cited in Strathern (1997)
The deeper challenge is not building a better benchmark — it is building agents that are genuinely reliable in the IID and OOD sense, not agents that score well on known benchmarks. Passk is a better proxy than Pass¹, but it is still a proxy.
17 / 18 — Summary
Key Results & Takeaways
#Finding
01 Pass¹ systematically overstates reliability. At p=0.82, Pass⁸ ≈ 20%. The gap is not noise.
02 Reliability gaps amplify with k. A 3pp difference at k=1 becomes 7pp+ at k=8 in relative terms.
03 Adversarial users reduce pass rates −15 to −30pp and increase variance across models.
04 Model ranking can invert between k=1 and k=8 on specific task subsets. Validate at deployment k.
05 Statistical precision requires ~400 trials at k=8 for ±5pp CI. Budget evaluation cost accordingly.

Ask:
